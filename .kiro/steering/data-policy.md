# 전남대학교 Kirothon 데이터 사용 및 백업 규칙

## 기록 저장은 주제에 따른 선택 사항

- 공통 템플릿의 기록 CRUD와 AI 결과 저장은 활용 가능한 예제 기능이며, 모든 팀의 필수 구현 요구사항이 아니다.
- 일회성 입력과 AI 응답만 필요한 서비스는 기록 저장 기능을 사용하지 않거나, 팀 주제에 맞춰 변경할 수 있다.
- POST /api/ai/generate는 기록 생성 없이 사용한다. 입력·결과를 Record에 저장하지 않지만 호출량 DB에는 횟수가 남는다. AWS 제공자 측 처리·보관 정책까지 무저장을 보장하는 API는 아니다.
- 팀 주제의 신규 테이블은 app/team/models.py로 확장한다. 로컬 DB와 서버 DB는 분리하고, 이미 배포된 컬럼·제약조건 변경은 멘토 검토를 거친다.
- 현재 공통 앱의 CRUD·SQLite 연동은 유지한다. 이 규칙을 이유로 기존 코드·DB·데이터를 자동 삭제하거나 저장 기능을 임의로 끄지 않는다.
- 주최 측의 사전 데이터 제공을 전제로 기능을 설계하지 않는다. 서비스 사용 중 발생한 데이터 저장과 사전 데이터 제공은 구분한다.
- 기존 EC2 안의 SQLModel/SQLite를 우선 사용한다. 기록 저장을 위해 별도 RDS·Redis·벡터DB를 기본 추가하지 않는다.

## AI 호출량 제한은 별도로 유지

- 기록 저장 기능의 사용 여부와 관계없이 공통 FastAPI의 AI 호출량 제한은 유지한다.
- 현재 한도는 서버별 분당 20회, 한국시간 기준 하루 600회이며, 기본 공통 API의 응답 상한은 256토큰이다.
- 기록 DB와 호출량 DB는 별개다. 기록 기능을 변경하거나 코드 롤백을 하면서 호출량 DB를 삭제·초기화·과거 값으로 되돌리지 않는다.
- ai_quota.sqlite3는 첫 제한 적용 요청 때 생성되는 현재 구조를 존중한다. 파일이 없다는 이유로 빈 운영 DB를 임의 생성하지 않는다.
- 학생의 직접 boto3 사용은 금지하지 않지만, 이 호출에는 공통 API의 한도가 자동 적용되지 않는다. 호출량과 AWS 비용을 고려한다.
- AWS 인증은 기존 EC2 IAM 역할을 이용한다. 액세스 키를 새로 만들거나 코드·프론트엔드에 넣지 않는다.

## 백업 기본값

- 기존 서버 내부의 매시간 SQLite 자동 백업은 유지한다.
- S3 자동 백업은 선택 사항이며, 현재 기준 서버에는 적용하지 않는다.
- 테스트 JSON 업로드 성공을 실제 DB 전송 또는 자동 전송 허가로 해석하지 않는다.
- 별도 명시적인 운영자 요청 없이 S3 전송 스크립트·systemd S3 drop-in·버킷 정책·IAM·보관 기간 만료 삭제를 적용하지 않는다.
- 프로젝트의 파일 저장 기능으로 기존 팀별 S3 버킷을 활용하는 것은 별도 기능 요구사항에 따라 검토한다. S3 기능 자체를 일괄 금지하는 규칙은 아니다.

## 원본과 비밀정보 보존

- 코드 원본과 개발 이력은 로컬/Git에 유지하고, 공식 서비스 배포는 팀의 통합 담당자가 수행한다.
- PEM은 로컬에만 둔다. DB·.env·비밀번호·AWS 자격 증명·인증 파일은 Git 또는 코드 배포물에 포함하지 않는다.
- 서버 데이터는 /home/ubuntu/kirothon-data/에 보존한다. 배포 과정에서 SQLite 파일과 운영 환경설정을 덮어쓰지 않는다.
- 기존 Nginx Basic Auth와 127.0.0.1:8080 내부 서비스 설정을 임의로 해제·외부 공개하지 않는다.
