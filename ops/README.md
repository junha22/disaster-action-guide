# 운영자용 파일 — 학생 코드 배포와 별도

이 폴더가 있다는 이유로 운영 서버 설정이나 도구가 자동으로 변경되지 않는다.

## 포함 파일

- deploy.py: r1의 코드 전용 배포·롤백 및 운영 DB 보존을 유지하고 r2 사전 검사를 추가했다.
- backup_db.py, kirothon-db-backup.service/.timer: 기존에 검증한 로컬 SQLite 백업 원본.
- test_deploy.py, test_backup.py: 임시 폴더·모의 서비스 명령만 사용하는 회귀 검사.

## r2 배포 검사

app/schema_check.py가 있는 r2 소스는 기존 Python venv로 app을 import하고,
/home/ubuntu/kirothon-data/records.sqlite3의 컬럼 호환성을 읽기 전용으로 확인한다.
검사 프로세스에는 별도 임시 DB 경로와 mock 모드를 지정하고 EC2 메타데이터 인증 조회를 끈다.
학생이 모듈 import 시점에 운영 파일 쓰기나 직접 boto3 호출을 넣지 않도록 Steering을 준수해야 한다.
이 검사는 임의의 Python 코드를 격리하는 보안 샌드박스가 아니다.

서버의 기존 기본 DB 경로가 다르면 이 도구를 바로 설치하지 말고 먼저 실제 설정을 확인한다.
기본 models.py/database.py·잠금 파일 보호, 배포 전 백업, 헬스체크 실패 시 코드 복구는 유지한다.
구형 r1 아카이브에는 schema_check가 없을 수 있어 기존 보호 검사로 롤백할 수 있다.

## 적용 순서 — 아직 실행하지 않음

1. Windows에서 r2 소스 검증과 로컬 설치·모의 개발을 확인한다.
2. 1조 기존 도구·unit·Nginx·DB 경로와 해시를 읽기 전용으로 확인한다.
3. 기존 deploy.py를 별도 파일로 보관하고 r2 도구를 임시 경로에서 문법·테스트·해시 확인한다.
4. 운영자가 정확한 파일 하나를 교체한다. DB·환경설정·인증·IAM은 교체하지 않는다.
5. r2 앱 Check → Deploy 후 기존 기록 유지와 실제 Haiku 호출을 소량 확인한다.
6. 코드 롤백·재시작을 확인한 뒤 2조에 신규 설치한다.

이 패키지는 아직 신규 서버를 한 번에 구성하는 최종 설치 스크립트가 아니다.
다른 팀에 1조의 .venv/node_modules/운영 DB/PEM/인증 파일을 복제하지 않는다.
팀별 역할·S3·공인 IP·리전·비밀번호는 각 서버의 실제 정보를 확인해 별도로 구성한다.
